# fetch-data

将用户的数据分析问题转为结构化意图，并补全取数所需完整语义上下文，生成 NL2SQL prompt 与 SQL，执行后返回查询结果供下游分析。

## 前置条件

1. 确认用户的数据分析问题**明确**（要分析什么、大致时间/范围）。
2. 检查当前 Session 产物目录（系统提示中给出的绝对路径）是否**已包含全部所需分析数据**：
   - **已全部存在** → 直接使用这些文件，**结束取数**，不执行取数流程。
   - **有缺失** → 继续。

---

## 取数流程

> **存储约定**：**落盘生成 NL2SQL prompt 所必需的产物，以及据此产出的 prompt / SQL 本身**。文件命名由各步骤自行决定（建议语义清晰、便于追溯），但**目录不能错位**。
>
> 下文 `{workdir}` 即当前 Session 产物目录；**绝对路径以系统提示中「当前 Session 产物目录」为准**，在其下按相对布局落盘，不要写字面量占位符。
>
> | Step | 产物 | 存储路径 | 性质 |
> |------|------|------|------|
> | 1 | 结构化问题（含 Step 3 改写后的版本） | `{workdir}/steps/` | prompt 输入 |
> | 2–3 → 4 | 指标信息 + 已选表元数据（合并为 `context.json`，Step 3 后一次性写入；Step 2 / 3 期间只留在对话中，不落盘） | `{workdir}/data/raw/` | prompt 输入（业务图谱 / 物理表元数据）|
> | 4 | NL2SQL prompt | `{workdir}/steps/` | prompt 产出 |
> | 5 | 生成的 SQL | `{workdir}/steps/` | prompt 下游代码 |

### Step 1. 问题结构化

从用户的自然语言分析问题中抽取字段，结构化产物落盘到 `{workdir}/steps/`（属于步骤过程产物）。缺失字段填 `null`，不要省略键。

示例：用户问「5月 app端某模型对话用户数，人均对话次数和点赞率分别是多少？」

```json
{
  "question": "5月 app端某模型对话用户数，人均对话次数和点赞率分别是多少？",
  "domain": "产品A",
  "metrics": ["对话用户数", "人均对话次数", "点赞率"],
  "intention": "查询5月app端某模型的三个指标值：对话用户数、人均对话次数和点赞率",
  "tables": null,
  "scope": ["5月", "app端", "某模型"]
}
```

- `question`：原始问题。
- `domain`：问题面向的业务领域 / 数据来源，如 产品A、产品B。
- `metrics`：涉及的关键指标，如 DAU、次日访问留存率。
- `intention`：用户想完成的最终分析问题，如「数据在不同端的分布情况」。
- `tables`：用户点名的数据表，如 `["dws_chat_dau_1d"]`；未点名为 `null`。
- `scope`：数据限定范围（时间、地域、维度等）；未知项用 `null` 占位或省略该元素。
- **`metrics` 写法**：尽量使用数据分析问题中已存在的**标准指标名**（如 `DAU` / `对话用户数` / `次日访问留存率`），不要用自由发挥的同义改写，以免造成歧义，导致后续步骤理解出错。
- **`tables` 写法**：用户点名的表必须**原样写入**，禁止改写成「看起来像」的标准名或图谱里的近邻表。未点名则填 `null`，不要从指标公式反推填入。

### Step 2. 业务数据信息补全

将 Step 1 的结构化问题作为输入，从可用知识源补全取数所需的业务语义。使用 CM 前加载 `Skill(skill="cm-skills")`，工具选择、参数、方言、配方和错误处理统一遵循该技能；系统提示「当前数据源」已绑定或用户已选择数据源时，从本步骤起遵循其「SQL 操作的数据源一致性」规则检索和核对元数据。下文引用的配方均指 `cm-skills` 内当前后端的业务配方。本步骤只负责查清，结果暂存于对话中，Step 3 消歧后由 Step 4 一次性写入 `context.json`；需要补齐哪些事实见 Step 4「context.json」。

> **知识源优先级**（Step 2.1 和 Step 2.2 都遵循）：
>
> 1. **业务图谱语义区**（`Metric` / `MetricCaliber` / `Dataset` / `DatasetField` / `Dimension`）——首选，结果可直接使用。
> 2. **业务图谱物理区与数据源探针**——语义区缺失或没有命中时回退：`DataSource` → `Table` → `Column`；图里仍没有的，用 `execute_read` 做只读元数据探针（如 `information_schema` / `DESC` 一类；取列值时带分区过滤和 `LIMIT`）补全 Step 2.2；对于 Step 2.1 的指标语义，需自行结合列注释 / 命名推断。
> 3. **上下文信息**（如对话历史、用户先前提供的口径说明等）——仅当上述两者都拿不到时才允许使用，并且**必须**满足下面两条硬约束：
>    - **精确对应**：上下文里出现的指标名 / 表名 / 列名必须与本次要探查的目标**完全一致**（同名同义、口径一致），不允许拿"看起来差不多"的旧上下文凑数；
>    - **来源标注**：在 `context.json` 中，每个来自上下文的指标 / 表条目都要加 `"src": "context"` 显式标出，便于 Step 3 复核。
>
> 任一字段若三个来源都拿不到，按"未知（省略该键）"处理，**不得**用模型先验或想象填充，**不可捏造**。

#### Step 2.1. 指标信息补全

针对 Step 1 中的关键指标，按上述优先级查询其业务定义与计算口径。名称待确认时，以指标名、分析意图或原问题定位 `Metric` 候选，核对业务含义后补齐全部口径。

已知名称时，用 `cm-skills` 的「按名称或同义词找指标并带出全部口径」配方；从搜索定位到 Metric 时，用「从搜索结果继续查询」配方。`Metric.description` 常含「有效用户」等定义，务必保留。指标存在但没有口径行时，不要从列名臆造公式。

#### Step 2.2. 表元数据补全

针对 Step 2.1 中所有数据表，按上述优先级查询表与列级别的元信息。

优先用 `cm-skills` 的「数据集字段」配方（`Dataset` → `DatasetField`），图里没有该数据集时用「表与列」配方（`Table` → `Column`）。`Dataset.name` 与 `Table.name` 不同时，以可查询的 `Table.name`（含 schema 前缀）为准。图谱不返回列的取值；筛选 / 维度列的取值取自「维度」配方的 `value_example` / `total_value_marker`，或对该表做小范围只读探针。

**指定表可达性**（`tables` 非空时先做，再拉元数据）：

Step 1 的 `tables` 非空时，必须先按**原名**查这些表（图谱 `Dataset` / `Table` + 数据源探针），禁止先搜相关/可用表来填充本步骤产物。用户确认前不得进入 Step 3，不得用 Step 2.1 口径里的其他 `dataset` 顶上。

按探查结果处理：

- **可达** → 按原名继续补全表元数据。
- **各访问方式均无权限** → 立刻调用 `ask_user_question`，提供下列 option：
  - 已添加权限，重新尝试
  - 探索其他可用数据进行分析
  - 选「已添加权限，重新尝试」→ 不改 `tables`，重跑本步骤；选「探索其他可用数据进行分析」→ 才允许走 Step 3.2 选表。
- **表不存在 / 名对不上** → 立刻调用 `ask_user_question`，提供下列 option：
  - **最相关的一张表**。找不到可推荐表时省略此项。
  - 探索其他可用数据进行分析
  - 选了最相关表或结果含 `custom_text` → 写回 `tables`，重跑本步骤；选「探索其他可用数据进行分析」→ 才允许走 Step 3.2 选表。

**最相关表**（仅用于「表不存在 / 名对不上」的推荐 option）：相关优先指**名字像用户写的那张**。

候选池（按知识源优先级，不必全跑）：

1. 图谱 `Dataset` / `Table` 的名单（用 `cm-skills` 配方按域或名称片段取）。
2. Step 2.1 已有口径中的 `dataset`：只当候选，不能直接取数。
3. 图谱没有名单时，用数据源探针（`execute_read` 列表名）做同样比名。

从池里只留 1 张，按此顺序：

1. **表名接近（主规则）**：去掉 project 前缀后比较。共享词多、前缀/BU/粒度后缀相同（`dws_` / `_1d` / `_di`）、只差 1–2 个字符或明显漏写一段。例：`dws_chat_dau_1dd` → `dws_chat_dau_1d`。
2. **用户点名的字段对得上**：用户问题中给了字段时，用图谱「数据集字段」/「表与列」配方看候选是否含这些列。名字接近且字段对得上，优于只是名字像。
3. **语义贴合（并列时才用）**：描述（`description` / `comment`）与分析意图更贴合的候选、或 Step 2.1 formula 提到的表；表类型按 [`references/table-naming.md`](references/table-naming.md) 是否符合分析意图。

不要推荐（options 只留「探索其他可用数据进行分析」，手输走自动「其他」）：

- 候选都只是同域里主题完全不同的表
- 只有指标公式里的替代表，和用户写的名字对不上
- 图谱与数据源都没有可比名的表（名单为空）

#### Step 2.3. domain 校验

完成指标 / 表元数据补全后，回头检查 Step 1 结构化问题产物中的 `domain` 字段。`domain` 必须**唯一确定且非空**才能进入后续步骤。

逐项核对：

1. **非空**：`domain` 不是 `null` / 空串 / 占位符。
2. **唯一确定**：`domain` 取值唯一，没有出现"多个业务域并存 / 取值含糊"的情况。可借助 Step 2 探查到的指标 / 表元数据（如表名前缀、各表所属的 `Dataset.domain`）反向印证结构化问题里的 `domain` 是否自洽。

按校验结果处理：

- **唯一且非空** → 继续 Step 3。若 Step 2 的元数据指向的业务域与结构化问题里的 `domain` 不一致，按"取值含糊"处理（见下）。
- **为空 / 缺失** → **停下并调用 `ask_user_question`**，请其补充本次分析对应的业务域（options 使用 Step 2 元数据中的候选域，或 `cm-skills` 的「业务域列表」配方返回的 `Domain.name`；不足时补合理候选项），拿到工具答复后**原地写回** Step 1 结构化问题产物的 `domain` 字段，并在回复正文中记录该补充。**不要**替用户臆测 domain，也**不要**只用正文提问。
- **取值含糊 / 多域并存** → 同样**停下并用 `ask_user_question` 确认**唯一业务域，确认后写回 `domain`。

> domain 校验通过是进入后续步骤的前置条件；`domain` 仍为空时**不得**继续往下走。

### Step 3. 歧义消除

Step 2 完成后，**先停下来**对照原始问题与新得到的指标信息 / 表元数据核一遍：用户的指标 / 维度 / 时间口径在补全后的数据语义里是否还存在**多解**或其他理解偏差。有歧义就**先消除**，再进入 Step 4。本过程**严格**遵循搜索到的数据，**不可捏造**不存在的信息。

**输入**：Step 1 的结构化问题 + Step 2.1 查到的指标信息 + Step 2.2 查到的表元数据 + 原始问题
**产物**：
- 消歧结论在**回复正文**中说明（即便“无歧义”也要写），**不落盘**
- 必要时**原地改写** Step 1 在 `{workdir}/steps/` 下的结构化问题产物：把模糊词替换成确认后的标准 `metric_name` / `<列名>=<值>` 形式（改写的原值 / 新值在回复正文中说明）

#### Step 3.1. 分析意图歧义消除

逐项检查。以下情形只要需要用户确认，都调用 `ask_user_question`，以待确定选项作为 options（禁止只用正文提问）。

1. **指标指向不明**

用结构化问题中 `metrics` 里的每一项分析指标去和 Step 2.1 探查到的指标信息中的可用指标对比。若**多条**指标可对应同一分析指标（如“留存率”同时命中“访问留存率”、“使用留存率”）→ 有歧义。
- 若存在歧义，则调用 `ask_user_question`，以所有可用指标为 options 让用户确认（按系统提示的反问规则）。
- 若用户确认后，则将确认后的标准 `metric_name` 写回 Step 1 的结构化问题产物（是否需要重新补全见 Step 3.3「联动」）。

2. **指标聚合粒度不明**

对每个已能对齐到标准 `metric_name` 的指标，检查是否所需聚合粒度不明（如“一段时间的对话用户数”同时命中“日均对话用户数”“时段总和对话用户数”），且原始问题未明确选择哪一种 → 有歧义。BI 场景默认：
- 一段时间内的人数 / 次数等统计值 → **日均值**（如“对话用户数 → 日均对话用户数”）；
- 环比 / 同比的基础数据 → **均值**（如对话次数月环比，用该时段日均对话次数）；
- **基于用户数的比例**（如渗透率）→ **先算每天的比例，再对每日比例取日均**，而不是先把分子、分母各自取日均（或求和）再相除（如每日对话用户数 / 每日访问用户数，再取日均）；
- **基于次数 / 时长的比例**（如点赞率）→ **先对时段内的分子、分母分别求和，再相除**（如该时段点赞次数总和 / 对话次数总和）。

如不被上述情况覆盖，则调用 `ask_user_question`，以所有可用聚合粒度为 options 让用户确认。

#### Step 3.2. 数据来源歧义消除

能按下方规则自动选定则不反问；仍无法消歧时，调用 `ask_user_question` 以候选为 options 让用户确认（禁止只用正文提问）。逐项检查：

1. **数据表来源不明**

数据中多个数据表在指标计算、数据维度选择等都满足数据分析需求。例如，分析“计算某产品不同端 dau 指标”，表 `xxx_index` 和 `xxx_distribution` 都包含可用于计算 dau 指标的数据，且包含指向不同端的字段，即两张表都可用于数据分析。
- 若 Step 1 的 `tables` 非空，且用户尚未改口（未选「探索其他可用数据进行分析」、未写回新表名），**不适用**本节自动选型；指定表不可达应已在 Step 2.2 停下确认。
- 自动选型依据：① 各表描述，选最符合分析需求的；② [`references/table-naming.md`](references/table-naming.md) 的表类型与命名结构（按表前缀解码表的特征与用途），选最符合分析需求的类型；③ 优先能够最准确计算指标的数据表组合，而不是只能计算某一“代理指标”的表。
- 若问题不被覆盖，则调用 `ask_user_question`，以所有可用数据表为 options 让用户确认。

2. **数据维度指向不明**

数据中多个维度可用于数据筛选。例如，分析“文本对话的点赞率”，“对话模式”和“对话类型”两个维度都包含“文本对话”的维度取值。用结构化问题中 `scope` 里每一项数据维度去和 Step 2.2 探查到的表元数据中的可用维度对比。若**多列**都能取到该值（如“文本对话”既在 `dialog_mode` 也在 `dialog_type` 里出现）→ 有歧义。
- 若存在歧义，则调用 `ask_user_question`，以所有可用维度为 options 让用户确认。

> 上述只是最常见的情况，遇到其他模糊（如时间口径——“近 30 天”含不含今天、“上月”按自然月还是滚动 30 天；如统计口径——“用户数”是 `visit_usercnt` 还是 `visit_login_usercnt`）也要在本步骤用 `ask_user_question` 一并提出，不要改用正文清单。

#### Step 3.3. 消歧结论

无论是否触发消歧，都要在**回复正文**中说明以下内容：

- **检查结果**
  - 指标歧义：<无 | 逐条列出每个模糊指标命中的候选清单>
  - 粒度歧义：<无 | 按默认（写明采用的默认规则与场景）| 逐条列出每个模糊指标命中的候选 `metric_name` / formula>
  - 维度歧义：<无 | 逐条列出每个模糊维度命中的候选清单>
  - 数据表来源：<单一可用表，无需选择 | 候选表清单 + 最终选定表（组合）+ 选定理由（满足需求 / 描述更贴合 / 最准确计算指标·非代理指标 / 概览表兜底）>
  - 其他：<无 | 描述时间口径 / 统计口径等其他模糊>
- **用户确认 / 默认**：<原模糊项> → <最终选择>（例：`留存率` → `访问留存率`；`对话用户数` → `日均对话用户数`（按默认）；`文本对话` → `dialog_mode=文本对话`）
- **对结构化问题的修改**：<字段路径> 从 <旧值> 改为 <新值>；若无修改写“无”

> **联动**：出现下列任一情况，都意味着 Step 2 的指标信息 / 表元数据可能缺失对应元数据 → **回到 Step 2** 重新拉（含新指标所需的表元数据），再进入 Step 4：
> - 消歧后写回的 `metric_name` **未出现**在 Step 2.1 已查到的指标信息中（无论是改名、新增还是切换聚合粒度）；
> - 消歧后选定的数据表（组合）**未出现**在 Step 2.2 已查到的表元数据中，或其在 Step 2.1 指标口径里缺少对应 `dataset` 的计算口径（换表 / 新增表场景）。
>
> 若写回的 `metric_name` 已存在于 Step 2.1 已查到的指标信息中（包括聚合粒度消歧切到同一指标的另一个聚合粒度版本），且选定数据表的元数据与指标口径均已齐备，则无需重跑 Step 2。

### Step 4. NL2SQL Prompt 生成

先按下文「context.json」把 Step 2 / 3 确认下来的指标与表元数据**一次性**写成 `{workdir}/data/raw/context.json`，再用脚本渲染 NL2SQL prompt（`--output` 须位于 `{workdir}/steps/` 下），供 Step 5 整段交给 LLM：

```bash
python {skill-dir}/scripts/generate_nl2sql_prompt.py \
  --problem <{workdir}/steps/ 下 Step 1 结构化问题产物路径> \
  --context <{workdir}/data/raw/context.json> \
  --output  <{workdir}/steps/ 下的输出路径>
```

#### context.json

只含 NL2SQL 真正需要的信息：指标（名称、别名、含义、可用口径）、**已选定**数据表（可查询的表名、描述、列的类型 / 含义 / 取值）。示例：

```json
{
  "metrics": {
    "DAU": {
      "desc": "指定日期访问用户数",
      "alias": ["日活", "访问用户数"],
      "priority": "high",
      "calibers": [
        {"table": "dws_xxx_overview_1d", "expr": "visit_usercnt_1d", "window": "1d"}
      ]
    }
  },
  "tables": {
    "public.dws_xxx_overview_1d": {
      "desc": "日粒度概览表（日期 x 访问端）",
      "note": "2026-08 每个 terminal_type 各 31 行",
      "cols": {
        "ds": ["text", "日期分区 yyyymmdd"],
        "terminal_type": ["text", "访问端；'全部'=全端汇总", ["app", "web", "全部"]],
        "visit_usercnt_1d": ["bigint", "访问用户数"]
      }
    }
  }
}
```

书写规则：

- **省略空值**：不写 `null` / `""` / `[]`，缺键即未知。`priority` 仅 `high` 时写；`additivity`（如 `additive`）、`default: true` 仅图谱有值时写；`window` 无值时省略。
- **名称作键**：指标名（`Metric.name`）、可查询的物理表名（含 schema 前缀，如 `public.xxx`）作 map 的键。
- **字段映射**：`Metric.description` → `desc`，`Metric.synonyms` → `alias`，`MetricCaliber.dataset` / `expr` / `time_window` → `calibers[].table` / `expr` / `window`；`Dataset.description` / `Table.comment` → `desc`；`DatasetField` / `Column` → `cols`。
- **列为定长数组**：`[dtype, desc]`，需要给出取值的筛选 / 维度列写成 `[dtype, desc, values]`。`values` 取自「维度」配方的 `value_example` 或探针；「全部 / 汇总」这类取值的含义写进 `desc`（来自 `total_value_marker` 或探针结论）。`dtype` 与描述都为空的图谱噪声列直接跳过。取值仅为示例或采样，并非完整枚举。
- **只写选定的表与可用的口径**：`tables` 只含最终选定的表，`metrics[].calibers` 只保留 `table` 在 `tables` 内且表达式可直接用的口径（如 `count(distinct)` 无列名的不可用）。落选候选表不要写入，否则 NL2SQL 会被要求覆盖所有表。
- **不写过程信息**：不写 `metric_key` / `caliber_key` / `datasource_id` / `domain` / 选表理由等；理由已在 Step 3.3 的回复正文说明。
- **探针结论进 `note`**：数据覆盖、粒度、汇总行约定等写成表级一句话 `note`，不要逐列写。
- **来自上下文的条目**（知识源优先级第 3 级）：在该指标 / 表条目上加 `"src": "context"`。

### Step 5: SQL 生成

1. 读取 Step 4 在 `{workdir}/steps/` 下产出的 NL2SQL prompt 的**完整内容**，**不允许**对其内容做更改。
2. 把它**整段**作为 prompt 交给当前模型（不要节选、不要总结、不要在前面加额外指令）。
3. 查看 [`references/partition-query.md`](references/partition-query.md) 中的分区与查询策略，根据表后缀确定分区字段和 WHERE 写法，结合表类型确定查询范围。
4. 模型必须**只输出一条可执行 `SELECT`**。
5. 从模型回复中只截取 SQL 主体（去掉 ```sql``` 代码围栏、Markdown 注释、解释段），保存到 `{workdir}/steps/` 下（以 `;` 结尾）。
6. 不要二次改写 SQL；如果模型输出多条语句，回到 Step 4 检查 prompt，**不要**手工拼接。

### Step 6: 执行 SQL 并返回结果

按 `cm-skills` 的 MCP 工具参考调用 `execute_read` 执行 Step 5 保存的 SELECT（`datasource_id` 的取值规则见该参考；ODPS 使用数据源配置的 AccessKey/STS 凭证，不传执行项目参数）。取数流程只读。本节只规定业务流程的回退位置。

1. **执行成功，拿到非空行** → 按 `cm-skills` 读取结果文件并检查完整性后，交给下游分析。
2. **执行成功，但返回空结果集**（`row_count` 为 0，无 `file_path`）→ **不要假装成功**。按下列顺序排查：
   - 回到 Step 1，检查 `scope`（特别是日期）/ `metrics` 是否对齐；
   - 回到 Step 3，检查是否漏过歧义——例如指标 / 维度选错列；
   - 回到 Step 5，检查 SQL 的过滤条件；
   - 之后重跑 Step 2–6（若 Step 3 改写了 metrics 名单则必须重跑 Step 2，否则可从 Step 4 起跑）。
3. **执行错误，工具返回错误信息** → 按错误类型处理：
   - SQL 准入 / 语法 / 列不存在 / 类型不匹配（含 `SQL query failed`、被拒绝的写操作或多语句）→ 回到 Step 5 修正 SQL。
   - `SQL read is forbidden`（权限不足）、`Datasource is unavailable for SQL execution`（数据源不可用或 `datasource_id` 不对）→ 若 Step 1 的 `tables` 非空，回到 Step 2.2 的指定表可达性闸，用同一套 `ask_user_question` 确认，**不要**回 Step 2 重拉元数据从而换到别的表；否则核对 `datasource_id`（对照系统提示「当前数据源」）。
   - 其余「表 / 列名查不到」→ 回到 Step 2 重新拉表元数据。
   
   **不要**绕过 `execute_read` 这一标准执行通道（如改走 shell / `psql` / PyODPS 自行取数），那样拿到的结果既不可复现也无法被评测器审计。
