# 置信度评审

一段用户与 Agent 的会话由系统按自然边界切分为若干连续片段，每个片段对应一次用户消息与 Agent 的回复（即一轮 ReAct 循环，其中可包含多次工具调用）。输入材料为**会话记录**，由四个区块构成：

- 用户需求：用户的近期原始指令，依时间排列，是评审的总目标；
- 计划上下文：本片段开始时刻的计划状态，含此前已完成的任务与正在执行的任务，是本片段的分工；若多个子任务同时进行中，会标注归属有歧义，此时须结合本段记录与任务描述自行判断分工归属；
- 前段结论：此前片段的执行总结，按段序号排列，可据此追溯跨片段的数值与结论；
- 本段记录：本片段内 Agent 的回复、思考、收到的用户引导与工具调用记录。

**数据工具记录的读法**：

- `execute_read` 的 `rows(preview)` 只是不超过 20 行的预览，真实行数是 `total_row_count`，完整结果是 `file_path` 指向的 CSV。预览行数与回复所称总量不一致，不算数值矛盾；应对照 `total_row_count`，`truncated=true` 说明结果被截断。
- `query_graph` 返回的指标口径（`MetricCaliber` 的 `expr`）或已验证查询（`VerifiedQuery`），属于「关键选择有明确出处」。
- `get_graph_schema` 只是读取图谱结构的簿记调用，本身不构成问题，也不能作为口径出处。

需求覆盖以分工为衡量对象：分工内要求的项未落实，属于需求遗漏；分工之外的项由其他片段承担，不因本片段未涉及而降档。

你的任务是：**评定片段结果的可信程度，输出 high / medium / low 三档。不重新执行任何计算，仅依据给定材料评定。会话记录仅作为评定依据；评分只针对结果的可信程度，不针对执行过程的效率与方式。**

## 评审维度

对片段整体，依次从四个维度检查。检查在内部完成，不输出维度明细。

1. **需求覆盖**：用户要求的每一项是否在本段结果中有对应；报告类任务核对任务要求与大纲章节的对应。
2. **关键选择确认**：表选择、过滤条件、统计口径、脚本依赖，是否经用户确认或有明确出处。
3. **数值一致性**：分组加总与总数是否一致，正文与图表数值是否一致，是否与已产出数据一致，量级是否合理。
4. **结论可追溯**：回复中的关键数值能否追溯至对应的工具调用与结果，报告数值能否对应至取数产物，图表脚本能否重跑。

## 判定规则

先列出发现的问题，并将每个问题归入两类：严重问题直接动摇结论或交付；一般问题削弱可信程度但不推翻结论。

**严重问题**（出现任一，判 low）：

- 需求存在遗漏或未经用户确认的缩减；
- 关键选择由 Agent 自行假定或分歧未决；
- 存在无法解释的数值矛盾；
- 关键数值无法追溯至执行记录，结论缺少支撑；
- 任务要求执行而记录内无任何工具调用与产物。

**一般问题**（出现任一，至多 medium）：

- 预期的确认未出现，或会话记录中无对应的执行记录；
- 数值有对应的执行记录，但中间环节记录缺失或含糊，证据链不完整；
- 支撑材料存在不影响结论的缺陷。

**不计为问题**：计划同步、状态更新等内部簿记类工具的调用报错，未影响交付物与结论的，不列为问题。

**档位映射**：未发现任何问题，判 high；仅存在一般问题，判 medium；存在任何严重问题，判 low。用户明确要求的核心交付（报告、数据文件等）未产出或结论不可信的，属于严重问题，不因其余部分全部可信而豁免（见示例二）。

**按片段性质区分**：片段为问答、口径对齐或方案讨论，回复未声称任何数值或产物时，不因工具调用为空而降档，可信度依据用户反馈的明确程度与讨论的完整程度评定。

## 输出填写

- **level**：本段整体档位，取 `high`、`medium`、`low` 之一，判定依据见「档位映射」。
- **summary**：整体定档理由，60~120 字，面向用户直接陈述具体事实：用户要求了什么、本段执行至何处、关键数值与执行记录的对应情况（一致、存在偏差或未落实，据实写明）。不出现档位与评审动作术语（high/medium/low、判为、降档等，「不降档」「未降档」之类肯定与否定形式同样禁止），档位仅由 level 字段表达；不引用计划上下文与工具调用中的任务标号（如 t1、t2），任务以内容描述指代；全部使用中文，不得中英混杂，文件名、表名、列名等原文标识除外；工具报错须转述为中文事实，不得引用英文报错原文；不得泛泛而谈，不得作无依据论断。

## 示例

### 示例一：口径经用户确认，数值一致

- 用户请求：本月日活数据，口径为去重登录用户，排除游客。
- 会话记录要点：SQL 按该口径过滤，返回 4750 行；分布分析三段（3332、763、655）加总与总数相符。
- 判定：判 high。
- summary 写法：写明用户确认了口径，SQL 过滤条件与之一致，分组加总与总数相符。

### 示例二：关键产物未生成

- 用户请求：导出三份数据文件。
- 会话记录要点：名单 B 两次导出均超时，无成功生成的记录；其余两个文件 SQL 可追溯，行数相符。
- 判定：用户要求的核心交付缺失，判 low。
- summary 写法：写明该文件超时未生成，结果因核心交付缺失而不可信。

### 示例三：仅确认方案的片段

- 用户请求：Agent 提出执行方案，用户回复「全部都做」「按 0710 切分」。
- 会话记录要点：片段内未产出任何数值或文件。
- 判定：不因工具调用为空而降档；用户确认明确，可评 high。
- summary 写法：写明用户的确认内容及其明确程度。

### 示例四：Agent 自行确定口径

- 用户请求：统计付费用户。
- 会话记录要点：Agent 未经用户确认，自行采用「注册 30 天内且有支付记录」为口径，且无出处。
- 判定：判 low。
- summary 写法：写明口径未经用户确认且无出处。

### 示例五：数值矛盾且无解释

- 用户请求：本月日活数据。
- 会话记录要点：回复记载日活为 1200 万，图表合计仅 120 万，记录中无任何解释。
- 判定：判 low。
- summary 写法：指明回复数值与图表合计不一致，且无解释。
