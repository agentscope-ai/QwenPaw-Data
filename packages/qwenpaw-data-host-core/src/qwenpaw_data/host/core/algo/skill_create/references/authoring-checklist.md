# 本仓库的落地约定与校验清单

撰写后按清单自检，再交给宿主机械校验。

**技能的形态规范只有一份：`references/effective-skill.md`。** 它定义技能由哪些组件构成、frontmatter 写什么、正文承载什么、如何渐进披露。本文件**不新增任何形态规则**，只补两类内容：本仓库特有的落地约定，以及可机械核对的清单。内容边界见 `references/capture-boundary.md`。

章节怎么分、要不要 `scripts/` 与 `references/`，按形态规范和本技能的任务需要决定——不要照搬其它技能，仓库里的既有技能早于该规范，形态并不统一。

## description 的收敛要求

形态规范已要求 `description` 同时写清 WHAT 与 WHEN。触发条件只写在 frontmatter `description` 里。本仓库额外要求它**收敛**：写清适用的指标/动作/数据源，避免「涉及数据分析时触发」这类会与既有技能抢触发的写法。带一到两个真实用户说法作为触发示例。

## 脚本调用约定

脚本调用统一用仓库约定：

```bash
python <skill-dir>/scripts/<脚本名>.py --<参数> "<值>"
```

并紧随一张参数表（列：参数 / 说明 / 默认值，必填项标注 `(必填)`）。

## 本仓库的行文约定

形态规范已覆盖「简洁至上」与「单一信息源」，此处只补本仓库的措辞习惯：

- 中文、祈使句、可执行；不堆砌 `必须`/`禁止`，但在会导致错误结果的地方明确约束
- 解释**为什么**：让模型理解约束的动机，比罗列硬性条文更可靠
- 参数化优先：技能里出现的月份、产品码、阈值、目录，都应是参数或标注了适用范围的口径常量

## 校验清单

输出前按下列项自检，未通过先改再输出。

**捕获边界**
- [ ] 无 SQL 代码块（围栏标注 sql，或正文出现完整的 SELECT/FROM 查询）
- [ ] 无 `列 = '字面量'` 形式的过滤条件
- [ ] 无指标定义、计算口径、阈值取值
- [ ] 无列含义/枚举对照表，无维度到列的绑定
- [ ] 无产品、型号、事件、专有名词的解释或词表
- [ ] 无环境故障、凭据/网络问题、「工具坏了」这类无解决方案的负面断言
- [ ] pitfall 写的是 FIX（怎么做对），不是 refusal（做不到）
- [ ] 每条约束都有可观察的触发条件与具体动作，无「注意数据质量」式空话

**结构**
- [ ] frontmatter 含 `name` 与 `description`，YAML 可解析
- [ ] `name` 为小写连字符、≤64 字符
- [ ] SKILL.md 行数 < 500；单个 reference > 300 行时含目录
- [ ] 无 README/CHANGELOG 等辅助文档

**内容**
- [ ] `description` 同时写清 WHAT 与收敛的 WHEN，含真实用户说法示例
- [ ] 正文不写触发条件（应全部在 description）
- [ ] 每条口径/约束在技能卡中有证据锚点
- [ ] 无本次任务写死的取值（月份、日期范围、具体客户名、临时表名）
- [ ] 步骤骨架来自原始分析任务的泛化，不是局部失败恢复
- [ ] 复用既有能力处写明「按 `<技能名>` 执行」，不要改写那些技能

**捆绑资源**
- [ ] `scripts/` 中的脚本可独立运行，有 `--help`，只依赖标准库或已在仓库中使用的依赖
- [ ] SKILL.md 中每个脚本调用都配了参数表
- [ ] 有脚本时提供了 `## fallback`
- [ ] `references/` 每个文件在 SKILL.md 中被引用并说明阅读时机
