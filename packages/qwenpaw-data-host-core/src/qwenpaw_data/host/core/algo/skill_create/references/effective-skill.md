# 什么是有效的 Skill

本文档介绍有效 agent skill 应具备的形态。

## 关于 Skill

Skill 是模块化、自包含的目录，通过提供专项知识、工作流和工具来扩展 agent 的能力。可以把它理解为特定领域或任务的「上岗指南」——它们把通用 agent 转化为具备流程性知识的专项 agent，而这些知识是任何模型都无法完整内化的。

### Skill 提供什么

1. 专项工作流 — 针对特定领域的多步骤操作流程
2. 工具集成 — 与特定文件格式或 API 协作的说明
3. 领域知识 — 组织内部规范、表结构、业务逻辑
4. 捆绑资源 — 用于复杂和重复任务的脚本、参考文档与资产文件

## 各组件的角色

每个 skill 由少数几种组件构成。各自职责不同，组合起来形成分层体系：在保持上下文精简的同时，让深度知识在需要时可用。

```
skill-name/
├── SKILL.md（必需）
│   ├── YAML frontmatter 元数据（必需）
│   │   ├── name:（必需）
│   │   └── description:（必需）
│   └── Markdown 指令（必需）
└── 捆绑资源（可选）
    ├── scripts/          - 可执行代码（Python/Bash 等）
    ├── references/       - 按需加载到上下文的文档
    └── assets/           - 用于输出的文件（模板、图标、字体等）
```

### `SKILL.md` — 入口

`SKILL.md` 是唯一必需的文件，包含两部分，职责不同：

**Frontmatter（YAML 元数据）** — 始终对 agent 可见，即使在 skill 被激活之前（约 100 词）。

- **`name`**：唯一标识（小写、连字符、不超过 64 个字符）
- **`description`**：主要触发机制 — 说明 skill 做什么、何时使用

description 必须同时说明 **做什么（WHAT）** 和 **何时用（WHEN）**，并包含触发关键词。所有「何时使用」的信息都应写在这里，而非正文。正文仅在触发后加载，因此在正文中写使用条件无助于 agent 发现 skill。

**正文（Markdown 指令）** — 仅在 skill 被触发后加载（理想情况下不超过 500 行）。

- 核心工作流与流程性指引
- 指向捆绑资源的链接，并说明何时阅读或运行
- 在步骤不直观时提供简洁示例

正文承载**如何执行**；不应重复详细的参考材料，也不应放置用于输出的文件。

> 上述字数/行数为参考值，必要时可以适当超出。

**关键模式：**
- 保持 `SKILL.md` 在 500 行以内；若接近此上限，可增加一层层级结构，并明确指引使用 skill 的模型下一步该去哪里跟进。
- 从 `SKILL.md` 清晰链接到 reference 文件，并说明何时阅读
- 对于较大的 reference 文件（>300 行），应包含目录

### `scripts/` — 确定性执行

可执行代码（Python、Bash 等），用于需要确定性可靠执行或会被反复重写的任务。

- **何时纳入**：同一段代码会被反复重写，或需要确定性执行时
- **示例**：PDF 旋转任务中的 `scripts/rotate_pdf.py`
- **优势**：节省 token、确定性高，可在不加载到上下文的情况下直接执行
- **注意**：agent 仍可能需要阅读脚本，以便针对特定环境打补丁或做调整

### `references/` — 按需加载的知识

按需加载到上下文中、供 agent 参考和思考的长文文档与参考材料。

- **何时纳入**：agent 在工作过程中需要查阅的文档
- **示例**：`references/finance.md`（财务 schema）、`references/mnda.md`（公司 NDA 模板）、`references/policies.md`（公司政策）、`references/api_docs.md`（API 规范）
- **适用场景**：数据库 schema、API 文档、领域知识、公司政策、详细工作流指南
- **优势**：保持 `SKILL.md` 精简，仅在 agent 判断需要时才加载
- **最佳实践**：若文件较大（>1 万词），在 `SKILL.md` 中提供 grep 搜索模式
- **避免重复**：信息应只存在于 `SKILL.md` 或 reference 文件之一，不要两处都有。除非信息确实是 skill 的核心内容，否则详细材料应放在 reference 文件中——这样既保持 `SKILL.md` 精简，又让信息可被找到而不占用过多上下文。`SKILL.md` 中只保留必要的流程性指令和工作流指引；将详细的参考材料、schema 和示例移到 reference 文件。

### `assets/` — 输出资源

不打算加载到上下文中，而是用于 agent 最终输出中的文件。

- **何时纳入**：skill 需要在最终输出中使用某些文件时
- **示例**：`assets/logo.png`（品牌资产）、`assets/slides.pptx`（PowerPoint 模板）、`assets/frontend-template/`（HTML/React 脚手架）、`assets/font.ttf`（字体）
- **适用场景**：模板、图片、图标、脚手架代码、字体、会被复制或修改的样例文档
- **优势**：将输出资源与文档分离，使 agent 可以在不加载到上下文的情况下使用这些文件

### 组件如何协同

| 层级 | 组件 | 加载时机 | 承载内容 |
|------|------|----------|----------|
| 1 | Frontmatter | 始终 | 身份与触发条件（WHAT + WHEN） |
| 2 | `SKILL.md` 正文 | 触发后 | 核心工作流与导航 |
| 3 | `references/` | 按需 | 详细领域知识 |
| 3 | `scripts/` | 按需（常直接执行） | 确定性操作 |
| 3 | `assets/` | 按需（用于输出） | 模板与交付物文件 |

这种**渐进式披露**模式让上下文窗口保持聚焦：元数据始终占用很少；正文在触发后加载；捆绑资源仅在任务需要时加载或运行。

## 核心原则

### 简洁至上

上下文窗口要与系统提示、对话历史、其他 skill 以及用户请求共享。默认 agent 本身已具备足够能力 — 只补充它原本没有的信息。优先使用简短、具体的示例，而非冗长说明。

### 自由度与任务匹配

| 自由度 | 形式 | 适用场景 |
|--------|------|----------|
| **高** | 文字说明 | 多种做法均可；决策依赖上下文 |
| **中** | 伪代码或带参数的脚本 | 存在推荐模式；允许一定变化 |
| **低** | 固定脚本 | 操作易出错；一致性至关重要 |

### 单一信息源

每段信息只存在于一处：流程在 `SKILL.md`，细节在 `references/`，执行在 `scripts/`，输出材料在 `assets/`。

## 应避免的内容

Skill 只应包含 agent 完成工作所需的内容。不要添加 README、CHANGELOG 等辅助文档；不要写 skill 如何编写的元信息；不要重复 agent 已熟知的概念。
