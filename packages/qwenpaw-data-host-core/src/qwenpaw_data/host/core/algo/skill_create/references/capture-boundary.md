# 捕获边界

Skill 只沉淀**可复用的做事方式**。业务知识不进 Skill——它属于语义层、域知识包或数据字典，写进 Skill 会让技能绑死在一次任务的数仓与口径上，换个业务域即失效。

归纳与撰写都以本文件为准。

## 只沉淀这四类

| 类别 | 含义 | 判据 |
| ---- | ---- | ---- |
| 风格 | 结论如何组织与呈现、术语是否需主动解释、何时该反问 | 换个业务域仍然照做 |
| 步骤 | 被验证过的执行顺序与前置检查 | 步骤名里不含具体表名/指标名 |
| 工具用法 | 某工具/引擎怎么用才对，参数与调用顺序 | 描述的是工具行为，不是数据含义 |
| pitfall | 会出错的地方 + **FIX（怎么做对）** | 有可观察的触发条件和具体动作 |

## 不要捕获

| 禁止写入 | 示例（原样禁止） |
| -------- | ---------------- |
| 指标定义、计算口径、公式 SQL | 「有效付费 = 单客户单日付费 > 10 元」 |
| 维度怎么拆、绑哪一列 | 「按支付渠道拆，用 channel_type」 |
| 列含义 / 枚举 | 「payment_type=1 是支付宝」 |
| 该用哪张表 / 数据集、别用某层 | 「用户行为查 dws，不要用 ods」 |
| 业务域覆盖范围 | 「这是某运维域，管用量和错误」 |
| 整条金标 SQL / 标准问法 | 问句 + 人确认正确的 `SELECT …` |
| 产品 / 型号 / 事件 / 关系 / 词表 | 「某型号是 2026-01 旗舰版」 |

同样不要捕获：

- 某次任务的数仓/业务细节、专有名词解释、样例值穷举
- 环境依赖故障、凭据/网络问题、「工具坏了」这类没有具体解决方案的负面断言
- 瞬时错误、一次性任务叙事、未验证的失败路径当作最佳实践
- 把「拒绝/无法完成」固化成流程——要沉淀 **FIX（如何做对）**，不是 refusal

判据很简单：**这条内容换一个业务域、换一套表还成立吗？** 不成立就不写。

## 从业务事实到可复用做法

trace 里的证据几乎都是业务特定的。归纳不是照搬，而是把「这次遇到了什么」翻译成「下次该怎么做」。

| 观察到（禁止原样写入） | 应沉淀为（可复用） |
| ---------------------- | ------------------ |
| `ROUND(double, int) does not exist` | 该引擎除法结果取整前需显式 CAST；报此类型错先查参数类型，不要改写等价语法 |
| 「这张表没有 product 字段，加了报 column cannot be resolved」 | 不要把一张表的过滤模式套用到另一张表；下拆前先确认字段存在 |
| 「人均日均，要显示每日客户数」（用户纠正口径） | 聚合口径（人均/日均/总量）与展示粒度先与用户确认再执行 |
| 「月表与日表结果不同」 | 同一指标存在多个粒度来源时，主动说明差异并让用户选定，不要静默择一 |
| 「查询超时，漏了分区过滤」 | 大表查询前先确认分区键已参与过滤；超时先查过滤条件，不要先做语法优化 |
| 「vpu 是什么？」（用户追问术语） | 输出中首次出现缩写或内部术语时主动给一句解释 |
| 「有效付费 = 自某财年累计 ≥ 阈值」 | **不沉淀**——业务定义，由语义层/域知识包承载 |
| 「该产品码限定为某值」 | **不沉淀**——口径常量 |
| 「日表叫 xxx_di，月表叫 xxx_mi」 | **不沉淀**——表选择知识 |

注意最后三行：不是「换个写法保留」，而是**整条丢弃**。若筛除后可复用做法很少，仍要写一个更窄的流程技能（锚定原始任务的泛化步骤），不要停写，也不要把局部失败立成新技能主题。

## 反空洞规则

剥掉业务细节后，很容易滑向「注意数据质量」「确保口径一致」这类正确但无用的话。它们比不写更糟：占了篇幅，还让人以为技能里有内容。

每条沉淀必须同时给出**可观察的触发条件**和**具体动作**：

| 不合格 | 合格 |
| ------ | ---- |
| 注意数据质量 | 用户数聚合前先剔除脏标识（空值、带前缀的伪 ID），否则去重计数会偏高 |
| 确保口径一致 | 同一指标有多个粒度来源时，先向用户确认用哪一个再取数 |
| 合理使用工具 | 图谱查不到指标（`query_graph` 返回空行）时不要反复换同义词重试，改查 `Table` / `Column` 节点按元数据探查 |
| 处理好异常 | 报「字段不存在」时先确认字段是否属于当前表，而不是改写语法 |

自检问法：**读完这一条，一个没参与过本次任务的 agent 知道该在什么时候做什么吗？** 答不上来就删掉或补足。

## 判定顺序

归纳时对每一条候选内容依次问：

1. 它是业务知识吗（口径/维度绑定/列语义/表选择/域范围/金标 SQL/词表）→ 是则丢弃，记入技能卡的「已丢弃的业务知识」
2. 它是环境故障、瞬时错误或未验证的失败路径吗 → 是则丢弃
3. 它是 refusal（「做不到」）而不是 FIX（「这样做对」）吗 → 是则丢弃，或改写为 FIX
4. 剥掉具体取值后还成立吗 → 不成立则丢弃
5. 有可观察的触发条件和具体动作吗 → 没有则补足，补不出就丢弃
6. 有证据锚点吗 → 没有则丢弃

六问全过，才写入技能卡。
