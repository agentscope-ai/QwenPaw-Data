# 证据到技能：信号通道与技能卡

本文件定义 digest 各信号通道的归纳用途，以及中间产物「技能卡」的字段。宿主已压缩 digest；归纳前阅读。

**先读 `references/capture-boundary.md`**：它规定了什么能沉淀、什么必须丢弃。本文件讲的是「从哪里找线索」，边界文件讲的是「哪些线索可以写进技能」，两者配合使用。

## 信号通道

digest.md 的 8 个小节各自承载不同的归纳职责。**注意每个通道的产出都是「做事方式」，不是通道里的业务事实本身**——通道给的是原料，可沉淀物要经边界判定后才成立。

**§1 任务 + §4 工作流骨架决定技能主题**（名称、`description` 的 WHEN、步骤骨架）。§2 补充前置确认。§5 / §6 只提供 pitfall / FIX，**不得**成为技能名或步骤标题。不要平均用力，更不要把错误通道当成主通道。

| 通道 | digest 小节 | 应产出（做事方式） | 判读要点 |
| ---- | ---- | ---- | ---- |
| 初始任务指令 | 1 | **技能定位、触发场景、名称** | 技能要解决的问题本体。范围锚定它的泛化（如趋势 + 单指标 + 单维度下拆），而非 trace 里跑过的全部内容 |
| 用户后续轮次 | 2 | 需要前置确认的事项、呈现风格 | 用户纠正的地方写成「该先确认什么」，不是用户给的那条口径。不改变 §1 的主题 |
| 既有技能查阅 | 3 | 命名避让 | 只换更窄的 kebab 名。禁止改写、补丁或覆盖被查阅的技能 |
| 工作流骨架 | 4 | **执行步骤序列** | 与 §1 一起构成技能正文骨架；步骤名要抽象到不含表名与指标名 |
| SQL/执行产物 | 5 | 可选的工具用法 / pitfall | 失败→成功的差异写入 pitfall 表，不是技能主题；整条 SQL、表名、过滤常量一律不沉淀 |
| 错误聚合 | 6 | 可选的 pitfall + FIX | **辅助通道**。同类报错固化为「什么现象 → 先查什么」，挂在 §1/§4 的流程下；环境/凭据类故障丢弃 |
| 产物与交付 | 7 | 交付形式与落盘约定 | 沉淀「产出什么形态、放哪里」，不是这次产物里的业务内容 |
| 最终结论 | 8 | 呈现风格、结论组织方式 | 表格如何组织、术语是否解释、不确定性如何说明；结论里的数字与口径不沉淀 |

### 禁止把局部失败立成技能

若 digest 第 1 节是分析问题（趋势、对比、下拆、归因等），而拟定的技能名或首句是恢复类用语（`fallback`、`retry`、`error`、`semantic-layer`、`sql-fix`、失败恢复），必须否决，改从**泛化后的任务**重新命名。局部失败只进「pitfall 与 FIX」。

### 用户后续轮次的分类

脚本给出的标签是启发式的，必须按原文复核。四类的归纳去向不同：

| 标签 | 含义 | 归纳去向 |
| ---- | ---- | ---- |
| 疑似口径修正 | 用户纠正了计算口径或展示粒度 | 沉淀为「执行前需确认哪类参数」，**不写入那条具体口径** |
| 疑似缺陷反馈 | 产物出错、图表没渲染、结果不对 | 写入 fallback 或前置校验，避免重犯 |
| 疑似追问澄清 | 用户在问概念（如某缩写是什么） | **不是**流程缺陷。沉淀为「首次出现术语时主动解释」，**不写入该术语的解释本身** |
| 疑似新增子任务 | 用户追加了新目标（如「生成看板」） | 可能属于另一个技能。列为 `other_candidates` / `open_questions`，不要提问 |

误把「追问澄清」当成流程缺陷，会让技能塞进不必要的步骤；误把「新增子任务」并入主流程，会产出一个臃肿且难触发的技能。

### 失败率的判读

digest 顶部的「规模」行与第 6 节可算出失败调用占比。失败率高不代表本次交互失败，也不代表技能主题是排错。探查阶段的试错可以写成该分析流程下的 pitfall（「报某类错时先查什么」），但技能仍然是 §1/§4 的分析过程。

无人值守运行不向用户确认是否沉淀：始终写一份新的流程技能。

摘要不含原始 trace，也无法回查——锚点用于标注结论来源与后续人工核对，不要尝试读取 trace 文件。

## 从证据到可复用做法

判据不是「能不能泛化」，而是 `capture-boundary.md` 的六问。下表按证据形态给出处置：

| 证据形态 | 处置 | 说明 |
| ---- | ---- | ---- |
| 引擎/工具行为约束 | **沉淀** | 「该引擎除法取整需先 CAST」——描述工具行为，换业务域仍成立 |
| 报错 → 修复的差异 | **沉淀为 pitfall + FIX** | 「报字段不存在时先确认字段属于当前表，而非改写语法」 |
| 被用户纠正的执行前提 | **沉淀为前置确认项** | 「聚合口径与展示粒度先确认再执行」 |
| 呈现与交互习惯 | **沉淀为风格** | 「首次出现内部术语时主动解释」「多来源冲突时让用户选定」 |
| 指标定义、口径、阈值 | **丢弃** | 业务知识，由语义层/域知识包承载 |
| 表名、数据集、分层选择 | **丢弃** | 业务知识 |
| 列含义、枚举、维度绑定 | **丢弃** | 业务知识 |
| 整条金标 SQL | **丢弃** | 只留其中体现工具用法的那一条规则 |
| 产品/型号/专有名词解释 | **丢弃** | 词表不属于技能 |
| 一次性偶发错误、环境故障 | **丢弃** | 网络超时、凭据失效、单次 404 后恢复 |
| 本次任务取值与路径 | **丢弃** | 月份、输出目录、临时表名 |

丢弃的条目要记入技能卡的「已丢弃的业务知识」，让筛除动作可核对——否则口径很容易伪装成「步骤」偷偷混进技能。

同一事实只写一处：流程写进 SKILL.md，长篇做法写进 `references/`，可执行逻辑写进 `scripts/`。

## 技能卡字段

归纳产出，落盘为 `skill-card.md`。这是 digest 与最终 SKILL.md 之间的桥梁：先把证据结论化，再据此写作，避免边读边写导致的遗漏和臆造。

每条规则后用 `[锚点]` 标注来源，如 `[轮次32]`、`[成功SQL1]`、`[错误2]`。无锚点条目一律删除。

```markdown
# 技能卡：<技能名>

## 定位
- 解决的问题：<一句话，泛化自第 1 节任务，不含具体指标名与表名>  [轮次0]
- 与既有技能的边界：<只记重叠与命名避让，不改写那些技能>

## 触发
- 应触发：<3-5 个真实用户说法>  [轮次0/轮次N]
- 不应触发：<相邻但不该命中的场景>  [推断，写入 open_questions]

## 前置条件
- <开始前必须确认的事项，写「要确认什么」而非「答案是什么」>  [锚点]

## 可复用步骤
1. <必须改写第 1、4 节：确认参数 → 取数 → 分析 → 交付；抽象到不含表名/指标名>  [骨架/轮次]
2. ...
（本节不得为空。pitfall 不能代替步骤骨架。）

## 工具用法
| 工具/引擎 | 正确用法 | 锚点 |
| ---- | ---- | ---- |

## pitfall 与 FIX
| 可观察现象 | FIX（怎么做对） | 锚点 |
| ---- | ---- | ---- |

## 输出与呈现风格
- 交付形态与落盘位置：<形态，不含本次业务内容>  [第7节]
- 呈现约定：<术语解释、不确定性说明、冲突时如何提示>  [第8节]

## 捆绑资源候选（同时写入决策 `files[]`）

无证据则只列 `SKILL.md`，不要为凑数编脚本。脚本必须带 CLI `contract`。

- path: `SKILL.md` ｜ purpose: 整段分析流程 ｜ contract: （可空）
- path: `scripts/<name>.py` ｜ purpose: <被反复重写的逻辑> ｜ contract: `--flag` 列表  [证据]
- path: `references/<name>.md` ｜ purpose: <超长的做法说明> ｜ contract: 何时阅读  [证据]

## 已丢弃的业务知识
| 丢弃内容 | 类别（口径/表/列/词表/…） | 锚点 |
| ---- | ---- | ---- |

## 证据不足项
- <未被证据支持、需用户确认或后续验证的条目>
```

两条硬性字段：

- **「已丢弃的业务知识」不得为空**——真实 trace 几乎必然包含业务事实。该表为空说明筛除没有真正执行，或业务知识被改写成「步骤」混入了上面的章节。
- **「可复用步骤」不得为空**，且必须改写 §1+§4。若只有 pitfall 没有流程，说明主题偏了，应从原始任务重写步骤，而不是把失败恢复立成技能。
- 「pitfall 与 FIX」可选。有局部失败时写入；不能作为唯一非空的过程章节。

「证据不足项」不是可选栏位。如实记录归纳时拿不准的地方，比编一条看起来完整的规则有用得多——它明确告诉用户下一次该验证什么。
