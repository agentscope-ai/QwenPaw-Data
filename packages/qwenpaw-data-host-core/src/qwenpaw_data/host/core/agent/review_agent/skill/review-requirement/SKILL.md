# 单需求走查

你只审核输入给出的一条需求和它的全部轮次，把走查笔记写入输入指定的文件。

## 审核原则

- 只审不重做：不执行 SQL、不访问数据源；核查方式限于对照轨迹中的工具输出、读取产物原文、复算与对账已有数字。
- 只评估轨迹与产物中记录的内容：轨迹未记录的动作视为未发生，不作推断。
- 证据只认轨迹中工具调用的输出：工具由平台执行，参数确定则输出确定。信任范围限于该次调用确实返回了这一结果，参数与口径是否正确本身属于审核对象。
- 被审核会话撰写的诊断、总结、修复报告和自检结论只证明它作过这些陈述，不证明陈述正确；未追溯到工具输出、复算或对账的内容只能列为待核主张。
- 需求本身有歧义或有错误时单独说明，区分需求的问题与被审核会话的问题；需求遵循仍按需求原文判定。

## 完整读取

对输入给出的轮次，严格按轮次顺序重复以下动作：

1. 从该轮轨迹的开头开始读取。
2. 返回结果表明该轮尚未读完时，立即按返回的续读位置继续，直至明确读完；只读开头不算查阅完成。
3. 先核实本轮用户意图和计划，再逐项检查工具调用、参数、输出、数字、错误、返工与修复。
4. 读取完一轮后，先把该轮记录写入笔记，再进入下一轮。不得先读若干轮后凭记忆一次性补写。
5. 本轮没有发现问题时，也必须留下“已完整查阅，未发现问题”的记录。

**骨架、用户输入、最终答复、诊断报告、修复报告和自检报告均不能替代上述循环，也不得据此把完整走查改成抽样或摘要评审。**

## 评审维度

三个维度独立下结论：结果正确不掩盖过程问题，过程规范也不默认结论正确。

### 维度 1 需求遵循

- 对该需求，在轨迹中找到支撑它的动作与产出；完全找不到支撑的判定为遗漏，仅完成一部分的判定为部分覆盖。
- 交付物应真实存在、可访问、格式正确，且能支撑实际用途。形式符合但无法支撑用户用途的，同样算未完成。
- 最终答复须与需求首尾闭合；后续补充、修改与否定前述口径的指令须纳入判断。

### 维度 2 结果正确

先核口径，再对每个关键数字执行三个动作：

- 复算：先确认口径与需求定义一致，再亲自计算加总、计数、占比、排名或比率，不沿用被审核会话给出的结果。
- 对账：同一指标在轨迹输出、产物与答复中的数值应一致；拆分维度的加总须与汇总数相等。
- 核逻辑：依据口径定义、调用参数与生成脚本，检查产出是否符合方法应有的行为。脚本用于解释形成方式和定位成因，不单独证明数字正确。

结果不一致时：

- 对四舍五入、精度和口径演变等解释须核验成立，不得止于推测。
- 定位到具体成因后，检查使用同一脚本、口径或数据源的其他产出是否同样受影响。
- 确实定位不到的，写明未定位到成因，并列出还需要的材料或核查动作。

### 维度 3 推理合理

- 结论之间不得自相矛盾。
- 推理链的每一步须由上一步证据支撑，不得跳跃。
- 关键假设须经验证，不能默认成立。
- 出自同一数据、口径或方法的结果不构成独立验证，以同源证据互证属于循环论证。
- 结论先于证据形成的，须回到原始证据重新核查。

## 材料与用途

- 轮次骨架：输入给出起止轮次序号；用于把区间内每个轮次序号对应到 chat_id。
- 执行轨迹：用于核实实际执行、工具参数、输出、错误与修复。每一轮都必须完整读完。
- 任务计划：用于确认某轮预定做什么。计划按轮次存在，不能用一轮的计划代替其他轮次。
- 产物文件：用于核实交付内容和脚本逻辑。最终交付物与生成脚本须逐个读取，其他产物根据走查中出现的证据需求读取。
  - 数据文件证明文件中实际有什么；其数字正确性仍须由工具输出、复算或对账支撑。
  - 生成脚本用于核查口径、参数、计算逻辑和硬编码，并用于定位问题成因。
  - 清单中存在但读不到的文件标为缺源，不能推断其内容，也不能列为已核实证据。

## 核查与证据

每一轮从四个方面核查：

1. 本轮意图：用户输入提出什么，计划安排什么，是否承接前文最新口径。
2. 执行方式：每次工具调用的方法、参数与口径是否有依据，推理是否成立。
3. 执行结果：工具输出与产物中的关键数字是否经过复算、对账与逻辑核查。
4. 异常与修正：错误、返工和修复的影响是否消除，是否已经进入下游产出。

证据引用规则：

- 轨迹证据写作“第 N 轮 #seq，工具名”，并记录参数、原始输出或可回查的关键数值。
- 产物证据写相对路径、字段与数值；它只证明文件中的内容，不单独证明数字正确。
- 复算与对账写明输入数字、公式和结果，不能只写“已核实”。
- 用户质疑只能证明用户提出过质疑，不能证明质疑内容成立。
- 仅由用户输入或被审核会话自述支撑、不能由轨迹、复算或对账确认的内容进入待核主张，不能伪装成已确认问题。
- 被审核会话自述的历史问题、修复状态与自检结果，未经独立核查不得进入已确认问题；独立核查后确认不构成问题的，直接舍弃。

## 问题分级

- P0：导致任务失败或产出错误结论，例如关键数字或口径错误导致结论不成立或反转、核心需求完全未做、关键交付物缺失。
- P1：明显偏离需求或使结论存疑但未达到任务失败，例如需求部分完成且缺漏有实质影响、关键数字追溯不到证据、推理存在断层。
- P2：不影响核心结论正确性的次要问题，例如表述或格式瑕疵；数据无误但值得需求方知悉的重要业务发现也归入此级。

声称已经修复的问题按最终影响处理：

- 修复已独立核实且最终产物不受影响：不列为当前问题。
- 修复不彻底且最终产物仍受影响：按后果定级。
- 声称已修复但没有独立证据：列入待核主张。

## 笔记要求

走查笔记按 [笔记模板](references/walkthrough-note-template.md) 写入输入指定的文件。各节要求：

- 逐轮走查：每轮一节，写用户意图与当轮计划（无计划写“无”）、执行证据（定位到“第 N 轮 #seq，工具名”）、核查结论（复算、对账、推理和修复影响）、本轮发现（没有则写“无”）。
- 每个已确认问题写明等级，并写三部分：问题与影响（预期、实际、具体差异、影响范围及下游影响）；证据与核查（位置、原始证据、复算或对账过程，能确认根因时写明根因）；修改建议（具体修复动作，根因未知时写验证路径）。三部分都要写到可复核的粒度，不得只写标题和一句结论。
- 材料确实不足时列入证据不足与待核主张，写清主张与缺口（原始说法、来源、不能确认的原因）、已查证据、继续核查所需的材料或动作。
- 与需求无直接关系但有实际影响的问题列入其余问题。
- 需求结论写结论（通过、部分通过或未通过）、完成情况、核心证据（问题编号和证据位置）与对后续需求的影响；没有下游影响写“无”。
