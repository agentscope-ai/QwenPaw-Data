# 数据分析审核方法论

对已完成的数据分析会话进行审核：评估被审核会话是否完成了用户提出的需求，产出的数字与结论是否可信，并输出一份附带证据引用与问题分级的 Markdown 审核报告。

## 审核原则

- 审核的目标是全面、完整、客观地找出全部问题，不是效率。审核覆盖全程，不止于最终答复；中间轮次的细节同样会影响关键结论，因此每一轮都要查阅，不得只挑部分轮次看。
- **不得跳过走查。轮次再多、轨迹再长，也不得抽样、压缩覆盖范围或提前进入报告阶段。**
- **你只负责组织审核，每条需求的审查必须调用 `review_requirement` 工具完成**；你不得亲自执行逐轮走查，也不得以抽查轨迹代替。骨架、用户输入、最终答复、诊断报告、修复报告和自检报告均不能替代逐需求审核。
- 你只写 `requirement-map.md` 与 `review-report.md` 两个文件；不创建、补写或改写走查笔记。
- 已排除的疑点与已完整修复且无最终影响的事项不写入任何报告。

## 材料与用途

材料分次读取，不在开始时一次拉全。“分次读取”只表示按当前步骤和分页逐步读取，**绝不表示可以省略轮次或只看部分材料。**

- 轮次骨架：用于建立需求清单与划分连续区间。骨架中的用户输入可能截断，只用于定位，不能作为执行证据，也不能代替轨迹。
- 用户已确认的口径与 skill 修改：随骨架材料提供，是结果正确性的核查基准。与某条需求相关的口径须记入该需求的完整内容，随需求一并交给逐需求审核。
- 任务计划：用于确认某轮预定做什么。计划按轮次存在，不能用一轮的计划代替其他轮次。

## 审核计划

**顺序不可颠倒：先完成需求清单并落盘 `requirement-map.md`，再创建计划，最后开始逐需求审核。清单未落盘不得创建计划；计划未创建不得调用 `review_requirement`。**

计划必须反映真实执行顺序，不能只作为展示：

1. 计划按一条需求一项走查任务建立，末尾追加汇总任务。
2. 走查任务标题必须写明需求编号和轮次范围。
3. 走查任务可以同时推进多项，最多 3 项并行。不得将多项待处理任务连续批量标记完成。
4. 每项任务先进入进行中，完成该项的全部实际工作后再标记完成。

例：

- 走查需求 R1：第 1-a 轮，共 a 轮；
- 走查需求 R2：第 a+1-b 轮，共 b-a 轮；
- 读回全部笔记，归并问题并产出审核报告

全部走查任务的轮数之和必须等于会话总轮数；不相等时先补齐区间，不能推进走查。

## 评审流程

### 第一步：确定需求清单与轮次区间

需求遵循的基准按以下优先级确定：

1. 审核发起人给出的明确需求清单或意图。
2. 被审核会话各轮用户提出的目标与要求，包括补充、修改和否定前述要求的内容。
3. 被审核会话制定的任务计划。
4. 从最终产出反推的目标。
5. 数据分析通用规范兜底。

没有明确清单但可以重建时，在报告中标注为“推断”。完全没有需求线索时，不判定需求遵循，只评审结果正确与推理合理。

本步只使用轮次骨架建立需求清单和区间，不读取产物，也不提前对需求下结论。骨架截断导致需求边界无法判断时，可以读取提出或修改需求的那一轮来确认原始指令；这不替代该轮的完整走查，更不能据此省略其他轮次。

对每条需求划定轮次区间：

- 区间连续，边界落在用户意图变化的轮次。
- 全部区间首尾相接覆盖第一轮到最后一轮，不留空档、不重叠。
- 纯续跑、催促、确认和取消的轮次也必须归入某条需求。

划分粒度以分析目标为准：

- 分析目标或方法改变时另立一条需求。例如：用户推翻既有结论要求从头重做；用户在潜客挖掘之外新提出客户分层任务。
- 同一目标连续推进中的追问、口径纠正、样式调整、交付打包要求并入所处阶段的需求，不单独成条。例如：要求报告换成指定样式，并入报告产出所属的需求；质疑某数字口径并要求重算，并入该轮所属的分析阶段。
- 同一主题中断后再次提出的，按时间顺序与此前阶段拆开，不合并为一条。

将需求与区间写入 `requirement-map.md`。每条需求必须包含：

- 需求编号和完整需求内容。
- 连续、不重叠的轮次区间，记起止轮次序号。

**文件落盘前不得完成第一步；区间未完整覆盖全会话时不得进入第二步。**

### 第二步：调度逐需求审核

为每条需求各调用一次 `review_requirement` 工具。**并行发起：在同一轮回复中同时发出最多 3 个调用，不要等前一个返回再发下一个**；直至覆盖全部需求。每次原样传入该需求的：

- 需求编号。
- 完整需求内容。
- 轮次区间的起止轮次序号。

只有逐需求审核返回完成、且对应的走查笔记文件已生成时，对应走查任务才可完成。返回失败时修正输入并重试该需求；任一需求审核未通过时，不得进入报告阶段。

### 第三步：归并问题并产出报告

**进入本步前逐份读回 `requirement-map.md` 和所有走查笔记。任何需求没有独立笔记，都必须返回第二步，不能写报告。**

随后读取 [报告模板](references/report-template.md)，严格按模板产出 `review-report.md`。

报告由笔记归并而来：

- 需求结论取自对应需求笔记，不从对话记忆补写。
- P0、P1、P2 条目从笔记原样归并，保留问题与影响、证据与核查、修改建议三部分；只统一全局编号、合并真正重复的问题，不压缩成一句话。
- 问题等级以笔记为准，归并时不重新定级、不升降级。
- 报告不得出现笔记中不存在的新问题。发现遗漏时，返回对应需求重新审核并更新笔记，再重新归并。
- “证据不足与待核主张”和“其余问题”分别从各笔记对应章节归并，不能混入已确认的 P0、P1、P2。
- 走查中提出但经核查确认不成立的疑点直接舍弃，不写入任何产物；不得设置“已排除疑点”章节。
- 总体结论只能建立在逐条需求结论和已确认问题上。覆盖不完整或证据不足时，不得声称最终产物正确、问题已全部修复或整体可用。

## 报告要求

- 审核范围中的走查轮数与读取产物数按实际填写。只看过骨架不计入走查，只看到产物名称不计入已读取产物。
- 引用的产物须与实际文件逐一核对；不存在或读不到的标为缺源，不作为证据。
- 每个数字和结论须有笔记中亲自核到的支撑。核不到的删除确定性表述，或列入证据不足与待核主张。
- 使用流畅、完整、面向业务读者的中文。专业术语可以保留，不使用口语化或比喻性措辞，术语前后一致。
